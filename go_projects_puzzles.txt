PROJECT 0: memview
Concept: Memory layout, struct alignment, CPU padding
Difficulty: Beginner
Sessions: 1
================================================================================

DESCRIPTION
-----------
You will write a Go program that shows you how your structs actually sit in
memory. The goal is to make you SEE something that normally happens invisibly:
the CPU forces your data to be placed at specific memory addresses, and Go's
compiler silently adds invisible "padding" bytes between your struct fields to
make this happen. You already love questioning struct behaviour — this makes it
visible with numbers.

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
- You know structs already (deep). Good.
- You need one new package: "unsafe"
  unsafe.Sizeof(x)    → how many bytes does x take in memory
  unsafe.Alignof(x)   → what address boundary this type must start at
  unsafe.Offsetof(x.Field) → how many bytes from start of struct to this field
- That's it. No other new concept needed.

THE PUZZLE
----------
Puzzle 1 (the only one — 15 minutes):
  "Why does reordering struct fields change the struct's total size?"

  Step 1: Create two structs with the SAME fields but in different order:
    type BadLayout struct {
        A bool
        B int64
        C bool
    }
    type GoodLayout struct {
        B int64
        A bool
        C bool
    }

  Step 2: Print the size of each struct using unsafe.Sizeof
  Step 3: Print the offset of each field using unsafe.Offsetof
  Step 4: Stare at the numbers. Write in your notebook why they are different.

EXPECTED OUTPUT
---------------
Your program must print something like this (exact numbers must match):

BadLayout size:  24
  A offset: 0   (size 1)
  B offset: 8   (size 8)    <-- 7 bytes wasted between A and B
  C offset: 16  (size 1)    <-- 7 bytes wasted after C

GoodLayout size: 10
  B offset: 0   (size 8)
  A offset: 8   (size 1)
  C offset: 9   (size 1)    <-- only 0 bytes wasted

If your numbers are different from these: your struct definition is wrong.
Fix it before moving on.

NOTEBOOK QUESTION (write this down, one sentence answer):
  "Why does BadLayout waste 14 bytes even though the fields only add up to 10?"
  Answer you must write: "The CPU requires int64 to start at an address
  divisible by 8. So after bool A at offset 0, Go adds 7 padding bytes
  before B can start at offset 8."

GOOD CODE SIGNS (check these yourself):
  [ ] You used the unsafe package, not any third-party library
  [ ] You printed both size AND offset for every field
  [ ] Your output matches the expected output exactly
  [ ] You can explain the 7-byte gap without looking at notes
  [ ] Total lines of code: under 30. If more, you overcomplicated it.

BAD CODE SIGNS (if any of these are true, fix before moving on):
  [ ] You hardcoded the numbers instead of using unsafe.Sizeof
  [ ] You have a loop — this project needs no loops
  [ ] You imported anything other than "fmt" and "unsafe"

WHAT YOU JUST LEARNED (write in notebook):
  - CPU alignment: every type has a required starting address
  - Go compiler adds invisible padding to satisfy alignment
  - Struct field order affects memory usage — matters in high-performance code
  - unsafe package lets you inspect memory layout directly
  CS subject: Computer Organization & Architecture

PROJECT 2: httpfromscratch
Concept: HTTP/1.1 as a text protocol, parsing, routing
Difficulty: Medium
Sessions: 5
================================================================================

DESCRIPTION
-----------
You will extend your tinytcp server to understand HTTP. HTTP is not magic.
It is a text format. A browser sends a string like this:

  GET /hello HTTP/1.1\r\n
  Host: localhost:8080\r\n
  \r\n

Your server reads that string, parses it, and sends back another string:

  HTTP/1.1 200 OK\r\n
  Content-Length: 5\r\n
  \r\n
  hello

That is all HTTP is. After this project, "how does HTTP work" is a question
you can answer from memory with exact details.

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
  strings.Split(s, " ")    → split string by space
  strings.TrimSpace(s)     → remove leading/trailing whitespace
  strings.HasPrefix(s, x)  → check if string starts with x
  fmt.Sprintf(format, ...) → build a formatted string
  strconv.Itoa(n)          → convert int to string

No new Go concepts. You know everything needed. This is string manipulation.

PROJECT 3: mini-kvstore
Concept: In-memory database, WAL persistence, mutex for thread safety
Difficulty: Medium
Sessions: 5
================================================================================

DESCRIPTION
-----------
You will build a key-value store — the simplest possible database. It stores
string keys mapped to string values. Get, Set, Delete. That's it.

Then you will add two critical features:
1. Persistence: the data survives when the program crashes (Write-Ahead Log)
2. Concurrency safety: multiple goroutines can use it without corrupting data

After this project, when someone asks "how does Redis persist data" or
"what is a WAL" or "what is a race condition", you will answer from experience,
not from memorizing a definition.

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
  sync.Mutex             → a lock. Lock() before reading/writing. Unlock() after.
  os.OpenFile(path, flags, perm) → open a file for reading or writing
  os.O_APPEND|os.O_CREATE|os.O_WRONLY → flags to open file in append mode
  bufio.NewScanner(file)  → read a file line by line
  strings.Fields(line)    → split line by whitespace into []string
  defer mu.Unlock()       → unlock when function returns (learn this pattern)

THE PUZZLES
-----------
Puzzle 1: "Can a struct with a map be a database?"
  Build:
    type KVStore struct { data map[string]string }
    func NewKVStore() *KVStore
    func (s *KVStore) Set(key, value string)
    func (s *KVStore) Get(key string) (string, bool)
    func (s *KVStore) Delete(key string)
  In main: set 3 keys, get them, delete one, try to get the deleted one.

EXPECTED OUTPUT (puzzle 1):
  name: hashim
  city: hyderabad
  lang: go
  after delete — name: "" found: false
  city still exists: hyderabad

Puzzle 2: "What happens to data when the program stops?"
  Run your program. Set some keys. Now add os.Exit(0) at the end.
  Restart the program. Try to Get those keys.
  Output: data is gone. Feel the problem before solving it.

EXPECTED OUTPUT (puzzle 2):
  First run:   Set name=hashim, Set city=hyderabad
  Second run:  Get name → "" (not found)
               Get city → "" (not found)
  (This is the expected WRONG behaviour — data loss. That's the lesson.)

Puzzle 3: "Can I log every write to a file?"
  Add a log file. Every time Set or Delete is called, append a line to the file:
    "SET name hashim\n"
    "DEL name\n"
  Open the log file in append mode. Each run adds to it, doesn't overwrite.

EXPECTED OUTPUT (puzzle 3 — contents of kvstore.log after running):
  SET name hashim
  SET city hyderabad
  SET lang go
  DEL name

Puzzle 4: "Can I rebuild the database by replaying the log file on startup?"
  Add a loadFromLog() function. It reads kvstore.log line by line.
  For each "SET k v" line: call s.Set(k, v) — but without writing to log again
    (add a boolean parameter or a separate internal set to avoid log duplication)
  For each "DEL k" line: call s.Delete(k) — same
  Call loadFromLog() in NewKVStore before returning.
  Now restart the program. Data should survive.

EXPECTED OUTPUT (puzzle 4):
  First run:   Set name=hashim, Set city=hyderabad, close program
  Second run:  Get name → "hashim" (recovered from log!)
               Get city → "hyderabad" (recovered from log!)

Puzzle 5: "What breaks when 100 goroutines write at the same time?"
  Add this to main:
    var wg sync.WaitGroup
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func(n int) {
            defer wg.Done()
            s.Set(fmt.Sprintf("key%d", n), fmt.Sprintf("val%d", n))
        }(i)
    }
    wg.Wait()
  Run with: go run -race main.go
  You WILL see a DATA RACE error. Good. That's the lesson.
  Now add sync.Mutex to KVStore. Lock in Set/Get/Delete. Run -race again.
  Race must be gone.

EXPECTED OUTPUT (puzzle 5 — before mutex):
  WARNING: DATA RACE
  Write at 0x... by goroutine ...
  Previous write at 0x... by goroutine ...

EXPECTED OUTPUT (puzzle 5 — after adding mutex):
  (100 keys set successfully, no race warning)
  go run -race produces no warnings

GOOD CODE SIGNS:
  [ ] KVStore has a sync.Mutex field (not a global mutex)
  [ ] Every Set/Get/Delete locks the mutex and defers Unlock
  [ ] loadFromLog does NOT call the normal Set (would double-log)
  [ ] Log file opened in append mode (O_APPEND) not overwrite
  [ ] go run -race shows zero warnings after mutex added
  [ ] NewKVStore returns *KVStore (pointer), not KVStore (value)
  [ ] Total lines: under 80. If more, there's duplication.

BAD CODE SIGNS:
  [ ] Global mutex variable instead of field on struct
  [ ] Lock() without defer Unlock() — risky, will deadlock if function panics
  [ ] loadFromLog calls the public Set which writes to log — causes log explosion
  [ ] File opened in write mode (O_WRONLY without O_APPEND) — overwrites log
  [ ] No error handling on file open

OPTIMIZATION CHECK:
  Your Get should use Lock() too (not just Set/Delete). Why? A map read while
  another goroutine writes is still a race. RLock/RUnlock from sync.RWMutex
  is even better for read-heavy workloads — switch to RWMutex as a bonus.

WHAT YOU JUST LEARNED:
  - A hash map IS a database at its core
  - WAL: write to log before saying "done" — basis of all database durability
  - Race condition: two goroutines touching shared data simultaneously = corruption
  - Mutex: one goroutine at a time. The OS enforces this.
  - defer mu.Unlock(): always unlock, even if function panics
  CS subjects: DBMS (WAL, crash recovery, ACID durability), OS (mutex, semaphore)

PROJECT 4: goroutine-pool
Concept: Worker pool, semaphore, WaitGroup, bounded concurrency
Difficulty: Medium
Sessions: 3
================================================================================

DESCRIPTION
-----------
You will build a worker pool: a system that limits how many goroutines run at
the same time. You have 100 tasks. You want only 5 running at once. When one
finishes, the next one starts. This is exactly what your BITSTEK bug was about
— too many goroutines opening DB connections simultaneously.

After this project, "goroutine pool", "semaphore", and "bounded concurrency"
are things you can implement from scratch, not just name.

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
  Buffered channels: make(chan struct{}, 5) → channel that holds 5 items
  Sending to full channel BLOCKS until someone receives
  Receiving from empty channel BLOCKS until someone sends
  This is the semaphore pattern — this is how you limit concurrency
  sync.WaitGroup: Add(n) before starting, Done() when finished, Wait() to block
  time.Sleep(duration): simulate a task taking time

THE PUZZLES
-----------
Puzzle 1: "What is a buffered channel and how does it block?"
  Create a buffered channel with capacity 3.
  Try to send 5 items to it WITHOUT reading.
  What happens?

EXPECTED OUTPUT (puzzle 1 — intentionally deadlocks):
  sent 1
  sent 2
  sent 3
  fatal error: all goroutines are asleep — deadlock!
  (This is correct. The channel is full. Sending blocks forever.)

Now fix it: read from the channel in a goroutine, then all 5 sends work.
This is the core insight: buffered channel = limited resource pool.

Puzzle 2: "Can I limit concurrent goroutines to exactly 5?"
  Build a worker pool:
    sem := make(chan struct{}, 5)  // semaphore: max 5 concurrent
    for i := 0; i < 20; i++ {
        sem <- struct{}{}           // acquire slot (blocks if 5 already running)
        go func(id int) {
            defer func() { <-sem }()  // release slot when done
            doWork(id)
        }(i)
    }
  doWork should print "worker N started" and "worker N done", with a sleep.

EXPECTED OUTPUT (puzzle 2 — sample, order may vary but pattern holds):
  worker 1 started
  worker 2 started
  worker 3 started
  worker 4 started
  worker 5 started
  worker 1 done        <-- only after one finishes does the next start
  worker 6 started
  worker 2 done
  worker 7 started
  ...
  (At no point should you see "worker N started" for more than 5 without
   a "done" appearing between them)

To verify: add a counter. Use atomic.AddInt32 to count active workers.
Print it in doWork. It should never exceed 5.

Puzzle 3: "How do I know when ALL tasks are done?"
  Add sync.WaitGroup. wg.Add(1) before each goroutine. wg.Done() at end of
  goroutine. wg.Wait() after the for loop.
  Print "all 20 tasks completed" after wg.Wait() returns.

EXPECTED OUTPUT (puzzle 3):
  [all 20 "worker N started" and "worker N done" messages]
  all 20 tasks completed       <-- this line appears LAST, always

GOOD CODE SIGNS:
  [ ] semaphore is a chan struct{} (not chan int — struct{} uses zero bytes)
  [ ] sem <- struct{}{} to acquire, <-sem to release
  [ ] defer used to release semaphore (safe even if goroutine panics)
  [ ] sync.WaitGroup used correctly: Add before goroutine, Done inside
  [ ] "all tasks completed" always prints after last "done" message
  [ ] Active workers never exceed the pool size (verify with counter)
  [ ] Total lines: under 40.

BAD CODE SIGNS:
  [ ] Using time.Sleep to "wait for goroutines" instead of WaitGroup
  [ ] Releasing semaphore with defer inside the goroutine but AFTER work —
      correct but make sure Done() also inside goroutine, not outside
  [ ] Pool size hardcoded as a magic number — use a const WORKERS = 5
  [ ] No counter to verify at most N goroutines run simultaneously

OPTIMIZATION CHECK:
  Replace chan struct{} semaphore with a task channel (channel of functions).
  This is the proper worker pool pattern:
    jobs := make(chan func(), 100)
    for w := 0; w < 5; w++ {
        go func() {
            for job := range jobs { job() }
        }()
    }
    for i := 0; i < 20; i++ {
        jobs <- func() { doWork(i) }
    }
    close(jobs)
  This is cleaner. Try to rewrite to this pattern after puzzle 3 works.
  The semaphore version and the task channel version are both valid — know both.

WHAT YOU JUST LEARNED:
  - Buffered channel as semaphore: classic OS concurrency pattern
  - Bounded concurrency: exactly what DB connection pools do
  - Why your BITSTEK bug happened: no pool, goroutines opened infinite connections
  - WaitGroup: the Go way to wait for all goroutines to finish
  - chan struct{}: zero-size type, used as signal/semaphore, wastes no memory
  CS subjects: OS (semaphores, thread pools, Dijkstra's P/V operations)

PROJECT 5: mini-redis
Concept: All previous concepts combined into one real project
Difficulty: Medium-Hard
Sessions: 10 (2 weeks)
================================================================================

DESCRIPTION
-----------
This is your first real portfolio project. It combines everything:
- TCP server (tinytcp)
- Protocol parsing (httpfromscratch — but using Redis RESP format)
- Key-value store with WAL (mini-kvstore)
- Concurrent clients with worker pool (goroutine-pool)

You are building a simplified Redis that:
1. Listens on TCP port 6379 (Redis's actual port)
2. Accepts commands in RESP format (Redis's text protocol)
3. Executes SET, GET, DEL, EXISTS, KEYS commands
4. Persists data in a WAL log file
5. Handles multiple clients simultaneously

You can test it with the real redis-cli tool — it speaks the same protocol.

WHAT IS THE RESP PROTOCOL
--------------------------
RESP (Redis Serialization Protocol) is simpler than HTTP. It looks like this:

Client sends SET name hashim:
  *3\r\n        <- array of 3 elements
  $3\r\n        <- first element is 3 bytes long
  SET\r\n       <- first element: "SET"
  $4\r\n        <- second element is 4 bytes long
  name\r\n      <- second element: "name"
  $6\r\n        <- third element is 6 bytes long
  hashim\r\n    <- third element: "hashim"

Server responds OK:
  +OK\r\n       <- simple string response

Server responds with a value:
  $6\r\n        <- bulk string, 6 bytes
  hashim\r\n

Server responds nil (key not found):
  $-1\r\n       <- null bulk string

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
  Everything from Projects 1, 3, and 4. No new concepts.
  The only new thing is the RESP format — described above.
  strings.TrimSuffix(s, "\r\n") → remove trailing \r\n from a line

THE PUZZLES (week 1 — core functionality)
------------------------------------------
Puzzle 1: "Can I parse a RESP command from a client?"
  Write parseRESP(reader *bufio.Reader) ([]string, error)
  It should read the *3 line, then read each $N + value pair.
  Test by sending raw RESP with netcat or telnet.
  Print the parsed command as a []string.

EXPECTED OUTPUT (puzzle 1 — after sending *3\r\n$3\r\nSET\r\n$4\r\nname\r\n$6\r\nhashim\r\n):
  Parsed command: [SET name hashim]

Puzzle 2: "Can I execute SET and GET?"
  Wire up your KVStore from Project 3.
  handleCommand(cmd []string, store *KVStore) string
  If cmd[0] == "SET": store.Set(cmd[1], cmd[2]), return "+OK\r\n"
  If cmd[0] == "GET": return "$N\r\nvalue\r\n" or "$-1\r\n"

EXPECTED OUTPUT (puzzle 2):
  Send: *3\r\n$3\r\nSET\r\n$4\r\nname\r\n$6\r\nhashim\r\n
  Server prints: +OK
  Send: *2\r\n$3\r\nGET\r\n$4\r\nname\r\n
  Server prints: hashim

Puzzle 3: "Can I add DEL and EXISTS?"
  DEL key → deletes key, returns :1\r\n (integer 1 = deleted) or :0\r\n
  EXISTS key → returns :1\r\n or :0\r\n
  Test each with raw RESP input.

Puzzle 4: "Can I add KEYS command?"
  KEYS * → return all keys in the store
  Response format for array:

PROJECT 6: tiny-lexer
Concept: Compiler design, tokenization, AST, finite automata (TOC)
Difficulty: Medium-Hard
Sessions: 5
================================================================================

DESCRIPTION
-----------
You will build a lexer (also called tokenizer/scanner) and a simple evaluator.
A lexer is the first stage of every compiler and interpreter. It reads source
code as a raw string and breaks it into meaningful tokens.

Input:  "let x = 10 + 20 * 3"
Output: [LET, IDENT(x), ASSIGN, NUMBER(10), PLUS, NUMBER(20), STAR, NUMBER(3)]

Then you will write a parser that turns tokens into an AST (Abstract Syntax
Tree), and an evaluator that computes the result.

This is exactly what Go's compiler does to your code before running it.

WHAT YOU NEED TO KNOW BEFORE STARTING
--------------------------------------
  iota: used to create sequential integer constants for token types
  type TokenType int with const block using iota
  rune vs byte: a rune is a Unicode character, use rune for char-by-char reading
  unicode.IsDigit(r), unicode.IsLetter(r): character classification
  strconv.Atoi(s): convert string "42" to int 42

THE PUZZLES
-----------
Puzzle 1: "Can I define all the token types my language needs?"
  type TokenType int
  const (
      ILLEGAL TokenType = iota
      EOF
      LET
      IDENT    // x, y, myVar
      NUMBER   // 42, 100
      ASSIGN   // =
      PLUS     // +
      MINUS    // -
      STAR     // *
      SLASH    // /
      LPAREN   // (
      RPAREN   // )
  )
  type Token struct { Type TokenType; Literal string }
  Print a few tokens to verify the struct works.

EXPECTED OUTPUT (puzzle 1):
  Token{Type: 4, Literal: "x"}    // IDENT
  Token{Type: 5, Literal: "42"}   // NUMBER
  Token{Type: 6, Literal: "="}    // ASSIGN

Puzzle 2: "Can I tokenize a simple expression?"
  Write: func tokenize(input string) []Token
  It reads the input character by character.
  Skips whitespace.
  When it sees a digit: keep reading until non-digit, emit NUMBER token.
  When it sees a letter: keep reading until non-letter, emit IDENT or LET.
  When it sees +, -, *, /: emit the corresponding token.
  When it sees =: emit ASSIGN.
  When it reaches end of string: emit EOF.

EXPECTED OUTPUT (puzzle 2):
  Input: "let x = 10 + 20"
  Tokens:
    LET      "let"
    IDENT    "x"
    ASSIGN   "="
    NUMBER   "10"
    PLUS     "+"
    NUMBER   "20"
    EOF      ""

Puzzle 3: "Can I parse tokens into an AST?"
  For now, just handle arithmetic: "10 + 20 * 3"
  AST node types:
    type NumberNode struct { Value int }
    type BinaryNode struct { Left, Right Node; Op TokenType }
  Write a simple recursive descent parser that respects operator precedence:
    * and / bind tighter than + and -
  Result: BinaryNode(+, NumberNode(10), BinaryNode(*, NumberNode(20), NumberNode(3)))

Puzzle 4: "Can I evaluate the AST and get the right answer?"
  Write: func eval(node Node) int
  NumberNode → return its value
  BinaryNode with PLUS → return eval(left) + eval(right)
  BinaryNode with STAR → return eval(left) * eval(right)
  etc.

EXPECTED OUTPUT (puzzle 4):
  Input:  "10 + 20 * 3"
  Result: 70      <-- correct (20*3=60, then 10+60=70, not (10+20)*3=90)

Puzzle 5: "Can I add let variable assignment?"
  "let x = 10 + 5"
  "let y = x * 2"
  Store variables in a map[string]int.
  When evaluating an IDENT node: look it up in the map.

EXPECTED OUTPUT (puzzle 5):
  let x = 10 + 5    → x = 15
  let y = x * 2     → y = 30
  x + y             → 45

GOOD CODE SIGNS:
  [ ] Lexer, parser, and evaluator are separate functions or files
  [ ] Operator precedence is correct: 10 + 20 * 3 = 70, not 90
  [ ] EOF token is emitted at end of input (parser needs this to stop)
  [ ] Unknown characters emit ILLEGAL token, not panic
  [ ] Variables stored in map, not hardcoded
  [ ] Total lines: under 150 for all 3 stages combined.

BAD CODE SIGNS:
  [ ] Using strings.Split to tokenize — won't handle multi-digit numbers
  [ ] No operator precedence (everything evaluated left to right)
  [ ] Panicking on unknown input instead of returning ILLEGAL token
  [ ] Giant switch statement that handles everything — split into functions

OPTIMIZATION CHECK:
  1. Your lexer is a state machine. Can you draw it on paper?
     State: START → reading digit → NUMBER
     State: START → reading letter → IDENT/KEYWORD
     This is a Finite Automaton. This IS the TOC concept.
  2. Can your parser handle parentheses? "(10 + 20) * 3 = 90"
     Add this as a stretch goal.

WHAT YOU JUST LEARNED:
  - Lexical analysis: how every compiler reads source code
  - Tokenization: turning a raw string into structured data
  - AST: tree representation of code structure
  - Recursive descent parsing: the most readable parsing technique
  - Operator precedence: why * binds tighter than + in every language
  - Finite automata: your lexer's state machine IS a finite automaton (TOC)
  CS subjects: Compiler Design, Theory of Computation, Discrete Mathematics
